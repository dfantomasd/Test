# Architecture

## Overview

Flight Task Automation is split into two layers:

- `launcher.py` — operator-facing orchestration and batch control;
- `worker.py` — desktop integration, Excel/PDF handling, airport resolution and package assembly.

The public repository stops at the boundary where proprietary airline-system behavior would begin.

## Processing flow

```text
Operator
  |
  v
launcher.py
  |  writes local runtime config
  |  starts isolated worker process
  v
worker.py
  |
  +--> find/focus target Windows application
  +--> read active-flight metadata       [production integration]
  +--> trigger document actions          [production integration]
  +--> attach to generated Excel books
  +--> parse flight number / route
  +--> resolve airports and countries
  +--> validate route-specific document set
  +--> export sheets to PDF
  +--> merge PDF parts in temporary build directory
  +--> atomically move final PDF into output folder
  +--> write small JSON result payload
  v
Final document package
```

## Why a separate worker process?

The desktop automation interacts with external Windows applications whose state can be unpredictable. Running the document operation as a separate process gives the launcher a clear success/failure boundary and makes repeated batch runs easier to isolate.

## Excel integration

The production workflow does not recreate spreadsheets from scratch. It attaches to Excel workbooks generated by the source desktop application through COM. Required sheets can then be exported using Excel's native `ExportAsFixedFormat` operation.

Generated workbooks are closed with `SaveChanges=False` to avoid unintentionally modifying source documents.

## Airport resolution

Route text may contain city names, airport names, IATA codes or ICAO codes. The worker builds a searchable index from `airportsdata`, normalizes transliteration with `Unidecode`, and uses `rapidfuzz` matching to resolve a route point to structured airport metadata.

That metadata is used to identify whether a route contains a country outside Russia and therefore requires international-route logic.

## PDF assembly

PDF parts are merged into a temporary build directory first. Only after a complete merged file has been written is it moved to the final destination. This reduces the risk of leaving a partially written final package when document generation fails midway.

## Configuration and sensitive data

Runtime settings are deliberately small. Public configuration contains only non-sensitive options. Network locations should be supplied through environment variables rather than hard-coded into source code.

The public snapshot intentionally excludes proprietary menu mappings, templates, internal filenames, operational datasets, credentials and production logs.
